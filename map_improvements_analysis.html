Critical Findings — What is Missing or Broken

1
No node health/status indicator — all nodes look "up" regardless of state
all maps
High

Every node renders with the same border and fill color whether it was collected successfully, had SSH errors, timed out, or returned incomplete data. A NOC engineer cannot tell at a glance which devices have collection problems. In incident response this wastes critical minutes.

NOC impact: engineer must cross-reference failed_hosts list manually. Industry standard (Cisco Crosswork, Nautobot, Zabbix) is a colored status ring on the node — green=ok, orange=partial, red=failed/unreachable, grey=not scanned.
Before
All device nodes are identical blue/teal circles regardless of collection status. Failed hosts only appear in a text list in the sidebar.
After
Node outer ring color encodes status: green ring = fully collected, amber ring = partial/errors, red ring = SSH failed, grey dashed = not scanned. A small ⚠ badge appears on nodes with errors. Status is shown in tooltip on hover.
2
L3 standard shell has no path trace, no route table, no subnet table
L3 standard
High

The L3 standard shell (l3_map_shell.py) renders a map + a device sidebar but has no ability to: (a) trace a path between two devices, (b) view the full route table, (c) filter by VRF. The enhanced shell has all three. The standard shell is what most users will encounter first (it is the default render_l3_map_html function).

NOC teams spend up to 70% of L3 troubleshooting time navigating routing tables. Without a searchable route table inline, engineers must re-SSH to devices. The enhanced shell solves this but is not the default.
Before
Standard L3 map: canvas + sidebar only. No route table tab, no path trace, no VRF filter. To see routes, click a node and scroll the 30-route limit in the sidebar.
After
Promote enhanced shell as the default. Add a "Route Table" tab and "Subnet Table" tab (already in enhanced shell). Add path-trace button. OR: merge the enhanced shell's tab bar into the standard shell.
3
Protocol filter on L3 map is defined in PROTO_CLASS but never rendered as clickable buttons
L3 standard
High

The audit shows the standard L3 shell technically has PROTO_CLASS mapping but no actual protocol filter UI buttons. A network with OSPF + BGP + Static + Connected routes produces a cluttered map where routing protocol types are visually indistinguishable from each other (they all use the same edge color from the graph_builder, not from the JS). The engineer cannot hide "Connected" routes to focus only on OSPF topology.

On a production network with 50+ routes, the inability to filter by protocol makes the map a "hairball". Industry tools (Juniper NorthStar, Cisco WAE) all provide protocol-layer filtering.
Before
All edge types shown simultaneously. Edge colors come from graph_builder (OSPF=blue, BGP=red, Static=amber) but there are no buttons to toggle visibility by protocol.
After
Add protocol filter toggle buttons above the canvas: [OSPF ✓] [BGP ✓] [Static ✓] [Connected ✓]. Each click hides/shows edges and their isolated nodes. Already partially done in enhanced shell — port to standard.
4
No data-collection timestamp visible on the map canvas itself
all maps
Medium

Maps contain a generated_at timestamp in the bundle JSON but it is not displayed prominently on the canvas. The subtitle line shows "Offline · v7.3.2" but not when the data was collected. In a NOC, a map from 4 hours ago looks identical to one collected 30 seconds ago. This causes engineers to act on stale data.

A 4-hour-old map during an incident can show links as "up" that have since failed. The freshness banner in the L2 discovery map is the right pattern — it needs to appear in L3 maps too.
Before
Header shows: "NOC L3 Routing Map · subtitle · Offline · v7.3.2". No collection time, no staleness indicator.
After
Header shows: "NOC L3 Routing Map · 7 devices · Collected: 2026-09-03 14:22:05 (2 hours ago) [STALE]" — the "STALE" badge appears in amber if age > NST_STALE_HOURS. Green "FRESH" if recent.
5
Combined L2+L3 map has no correlation indication — physical and logical edges look identical
Combined
Medium

The combined map renders L2 edges (solid green) and L3 edges (dashed blue) together but there is no visual indication when an L3 route is correlated with a specific L2 physical link. The sidebar says "X correlated with physical links" as a number but doesn't highlight the correlation visually on the canvas.

The core value proposition of a combined map is showing "this OSPF adjacency runs over this physical cable." Without the visual correlation, the map is just two overlapping separate graphs.
Before
Physical edges = green solid. Routing edges = blue dashed. Correlated pairs show no visual relationship — you cannot tell that the OSPF adjacency between core-rtr-01 and dist-sw-01 runs over the Gi0/1 ↔ Eth1/1 cable.
After
When an L3 edge has a matching physical_link: (1) both edges glow together on hover, (2) clicking either edge shows "Physical: Gi0/1 ↔ Eth1/1 | Logical: OSPF area 0" in a correlation panel. A small chain-link icon ⛓ appears on correlated edge pairs.
6
Flow animation in L3 standard shell fires on "Toggle Flow" but moves random edges — not traffic-aware
L3 standard Flow map
Medium

The "Toggle Flow" button in the standard L3 shell randomly flickers edge widths (1px → 3px) via a 200ms interval. This is cosmetic noise with zero informational value. Per the steering rules: "Auto-play animations on the map" must not happen. The animation should only exist if there is actual traffic rate data, and it should animate along the edge direction.

Random flickering is distracting in a NOC context and gives a false impression of live data. It should be removed unless actual utilization data is present.
Before
"Toggle Flow" button randomly wiggles random edge widths at 200ms intervals. No relationship to actual traffic. No direction. Creates noise.
After
Remove random flow animation. Replace "Toggle Flow" button with "Traffic Overlay" that only activates when utilization data is loaded (same pattern as L2 map). If no data: button shows "(no data)" and is disabled.
7
showDetail() in L3 standard shell builds innerHTML from unsanitized DEVICES_META data
L3 standard
Medium

The detail panel JS in l3_map_shell.py uses template literals directly into detailContent.innerHTML with data from DEVICES_META[nid]. While script_safe_json escapes for script-breakout, it does NOT HTML-escape for DOM injection. A device with platform = "Cisco <b>evil</b>" renders raw HTML in the panel. The enhanced shell uses a topoEsc() function — the standard shell does not.

XSS risk: exploitable if device data contains HTML, though localhost-only deployment lowers exploitation probability. Still a correctness issue per steering rule 05.
Before
showDetail: html += `<tr><td>Platform</td><td>${m.platform}</td></tr>` — raw device string in innerHTML.
After
Add function topoEsc(s){return String(s||'').replace(/&/g,'&amp;').replace(/</g,'&lt;').replace(/>/g,'&gt;')} and wrap all data interpolations: ${topoEsc(m.platform)}.
8
No "copy to clipboard" or CSV export for route table / connection index
all maps
Low

Network engineers routinely need to share route tables and connection indexes in tickets, Slack, and change-management systems. None of the map shells provide a copy-to-CSV or copy-table function. The L2 map has a Print media query but no CSV export.

Engineers manually copy-paste table data into spreadsheets. A single "Export CSV" button on route/connection tables would save 5-10 min per incident.
Before
No export. Connection index and route explorer tables are view-only. Print CSS exists in L2 map but produces multi-page output.
After
Add "⬇ CSV" button above each table. JS serializes visible (post-filter) rows to CSV and triggers a browser download. One function, ~20 lines of JS.
9
Node shapes do not distinguish device roles visually — all devices are rectangles
L3 standard L2
Low

All device nodes use shape: 'box'. In the L3 map, subnets use ellipses and gateways use dots — this is good. But core routers, distribution switches, and access switches all look identical. Network engineers are trained to read role hierarchy visually (core = cylinder, router = hexagon, switch = square).

On a complex topology, role identification requires reading labels. Role-based shapes (already partially done via color) would allow faster pattern recognition — especially at scale.
Before
All devices: box shape. Differentiation only by color (cisco=teal, juniper=orange, nxos=indigo). Role (core/dist/access) not encoded in shape.
After
Core routers: hexagon. Distribution switches: diamond. Access switches: box. Edge/WAN routers: triangle. Colors remain the same. Shape + color = two independent channels for richer encoding.
10
L2 map "map looks the same as before" — because render_topology_page in topo_map_shell.py has its own legacy CSS not updated by standard_map_shell.py redesign
L2
High

The standard L2 map sample uses render_topology_page() from topo_map_shell.py, which has its own hardcoded HTML template with the legacy GitHub dark theme. The standard_map_shell.py redesign only affects the embed_standard_map_top_chrome() fragment used by report_formatter.py. The actual production L2 map HTML (generated by report_formatter.py) IS using the new CSS — but the render_topology_page standalone path (used by tests and the demo generator) still has the old look.

The standalone L2 map HTML files opened directly will show the old design. The production report path via report_formatter uses the new design. Both code paths need the same visual treatment.
Before
render_topology_page CSS: dark GitHub #0d1117 background, rounded card, 12px padding offset, old body layout. Does not use CSS variables or the new enterprise theme.
After
render_topology_page should inject standard_map_shell_css() for consistent styling. The body/layout/colors should match the production report_formatter path.
11
Hover tooltips show raw HTML strings — not formatted device info cards
all maps
Low

vis.js node title attributes contain HTML (e.g., "<b>core-rtr-01</b><br>Vendor: IOS...") but the rendering quality depends on the browser's vis.js tooltip renderer. In Chrome standalone HTML mode the tooltips appear as plain text boxes with no styling. The L3 shells build elaborate title HTML but it often doesn't render as intended because vis.js tooltips do not apply the page's CSS.

Rich hover tooltips are the primary way NOC engineers get device context without clicking. Broken/ugly tooltips reduce map utility.
Before
Hover → small vis.js default tooltip box, plain text, no styling, content runs off-screen if long. HTML tags sometimes rendered raw.
After
Implement custom tooltip div: on network.on('hoverNode'), show a styled div absolutely positioned near the cursor with the formatted device card (platform badge, IP, route count, protocols). Remove from title attribute — use the JS handler instead.
12
Subnet nodes show no gateway/routing information on hover
L3
Low

Subnet nodes (purple ellipses) carry SN_META data including gateway IPs, advertising devices, prefix length, is_private, route_count. This data is only visible in the sidebar detail panel after clicking. For fast scanning, engineers need to see "this is 192.168.10.0/24, /24, private, GW=172.16.1.1, 3 devices" without clicking.

Before
Subnet ellipse hover: tooltip shows "Subnet 192.168.10.0/24" — just the ID repeated.
After
Custom tooltip card: Subnet | /24 | 256 hosts | Private | GW: 172.16.1.1 | 3 devices advertising. Appears on hover without clicking.

Priority Recommendation

Implement in this order for maximum NOC value per effort:

  1. Finding #10 — Fix render_topology_page CSS (30 min, makes L2 sample maps actually reflect the redesign)
  2. Finding #3 — Add protocol filter buttons to L3 standard shell (30 min, high NOC value)
  3. Finding #4 — Add collection timestamp + staleness badge to all map headers (20 min)
  4. Finding #7 — Add topoEsc() to showDetail() in L3 standard shell (15 min, security)
  5. Finding #6 — Remove random flow animation, disable button when no data (10 min)
  6. Finding #1 — Node health ring encoding (1 hour, highest NOC impact)
  7. Finding #2 — Make enhanced shell the default L3 map (route table + path trace) (1 hour)
  8. Finding #8 — CSV export (30 min)
  9. Finding #5 — Combined map correlation highlighting (2 hours)
  10. Finding #9, #11, #12 — Node shapes, tooltip polish (ongoing)
Note on findings #2 and the "enhanced vs standard" split: The current design has two parallel L3 shell implementations — the standard shell (l3_map_shell.py) and the enhanced shell (l3_map_shell_enhanced.py). The enhanced shell already has path trace, route table, VRF filter, and layout algorithms. The fastest path to parity is to update the web API endpoint (vlan_checker_web.py) to use the enhanced shell as the default for all L3 map renders, keeping the standard shell as a fallback. No feature duplication needed.
